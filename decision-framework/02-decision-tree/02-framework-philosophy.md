# 2. Framework Philosophy

## Core Principles

### 1. Process Over Personality

Frameworks reduce cofounder friction by providing neutral procedural ground. When passionate cofounders disagree, the framework becomes the referee, not the individuals.

**Why This Matters:**
- Early-stage startups often have cofounders with strong convictions
- Disagreements can become personal without structured processes
- Frameworks provide objective criteria for decision-making
- Preserves trust and relationship health

### 2. State Before Solution

Never apply a decision framework without first gathering context. Jumping to solution selection without understanding the problem state leads to wrong-tool-for-the-job errors.

**Why This Matters:**
- Different decisions require different frameworks
- Context determines appropriate methodology
- Prevents analysis paralysis from over-engineering simple decisions
- Prevents rash decisions on complex issues

### 3. Tool Appropriateness

Different decisions require different frameworks; no one-size-fits-all. The meta-framework ensures we select the right tool based on decision characteristics.

**Why This Matters:**
- Using STOP for a $5K decision wastes time
- Using 5-Minute Rule for a $500K pivot risks the company
- Framework selection is itself a critical decision
- Optimizes for decision quality vs. time investment

### 4. Auditability

Every critical decision must be documented for investor transparency. Future investors, board members, and team members need to understand how decisions were made.

**Why This Matters:**
- Investor due diligence requires decision transparency
- Board oversight needs documented rationale
- Team alignment benefits from visible decision logic
- Legal and regulatory compliance may require records

### 5. Continuous Improvement

Retrospection ensures framework efficacy over time. We learn from each decision and refine our processes.

**Why This Matters:**
- Early-stage startups iterate rapidly
- What works at seed stage may not work at Series A
- Frameworks should evolve with the company
- Prevents process stagnation

## The "Meta" Approach

### Traditional Framework Problem

Most startups adopt a single decision framework (e.g., "we always use RAPID" or "we always consensus"). This creates problems:

- **Over-engineering:** Simple decisions get complex processes
- **Under-engineering:** Complex decisions get simple processes
- **Misalignment:** Framework doesn't match decision type
- **Frustration:** Cofounders feel the process is wrong for the situation

### Meta-Framework Solution

Our meta-framework treats framework selection as a decision itself:

```
DECISION → STATE ASSESSMENT → FRAMEWORK SELECTION → FRAMEWORK APPLICATION → RETROSPECTION
```

This ensures:
- Each decision gets the right process
- Framework selection is systematic, not ad-hoc
- We learn which frameworks work for which contexts
- Process scales with company complexity

### The Three-Layer Model

```
Layer 1: Meta-Framework (This Document)
    ↓ Selects appropriate framework based on context
Layer 2: Decision Frameworks (STOP, ASOFF, ICE, etc.)
    ↓ Provides structured decision methodology
Layer 3: Decision Templates (Specific documentation)
    ↓ Captures decision process and outcome
```

## Decision Dimensions

Our meta-framework categorizes decisions along three key dimensions:

### Dimension 1: Reversibility

How easy is it to undo this decision?

- **Type I (Two-way door):** Easily reversible, low cost (<$10K, <1 week)
- **Type II (One-way door moderate):** Reversible with significant cost ($10K-$100K, 1-4 weeks)
- **Type III (One-way door significant):** Difficult to reverse ($100K-$1M, 1-3 months)
- **Type IV (One-way door critical):** Nearly impossible to reverse (>$1M, >3 months)

**Philosophy:** Reversible decisions should be made quickly with lightweight frameworks. Irreversible decisions deserve thorough analysis with heavyweight frameworks.

### Dimension 2: Risk

What is the potential impact if this decision goes wrong?

- **Low Risk (Score 5-8):** Minimal financial, timeline, team, customer, or strategic impact
- **Medium Risk (Score 9-12):** Noticeable impact across one or more domains
- **High Risk (Score 13-16):** Significant impact across multiple domains
- **Critical Risk (Score 17-20):** Existential threat to the company

**Philosophy:** Higher risk justifies more time and more robust frameworks.

### Dimension 3: Alignment

Are cofounders aligned on the problem statement?

- **Full Alignment:** Shared understanding of problem and success metrics
- **Partial Alignment:** Agreement on problem but not on approach
- **No Alignment:** Disagreement on fundamental problem statement

**Philosophy:** Alignment issues must be resolved before framework application. Use Alignment Resolution Protocol when needed.

## Framework Design Principles

### Principle 1: Time Boxing

Each framework has a defined time investment. Exceeding this triggers escalation.

**Why:**
- Prevents analysis paralysis
- Forces prioritization
- Creates urgency
- Respects cofounder time

### Principle 2: Documentation Requirements

Each framework has minimum documentation standards.

**Why:**
- Ensures auditability
- Facilitates retrospection
- Enables knowledge transfer
- Supports investor due diligence

### Principle 3: Sign-off Requirements

Critical decisions require explicit sign-off from both cofounders.

**Why:**
- Creates commitment
- Documents agreement
- Prevents ambiguity
- Supports accountability

### Principle 4: Retrospection Triggers

Certain frameworks require mandatory retrospection.

**Why:**
- High-stakes decisions need review
- Framework effectiveness needs validation
- Process improvements need identification
- Trust needs reinforcement

## The 4X Game Analogy

We borrow concepts from 4X strategy games (Civilization, Stellaris, etc.):

### Turns
Each decision is a "turn" with opportunity cost. Time spent on one decision is time not spent on others.

### Map Vision
State gathering provides "map vision" - understanding the terrain before moving.

### Win Conditions
Clear success metrics define our "win conditions" for each decision.

### Technology Nodes
Frameworks are "technology nodes" - unlocked based on context and prerequisites.

**Why This Analogy:**
- Familiar to many technical cofounders
- Emphasizes strategic thinking
- Highlights opportunity cost
- Makes abstract concepts concrete

## Anti-Patterns to Avoid

### Anti-Pattern 1: Framework Shopping

**Description:** Trying different frameworks until you get the answer you want.

**Solution:** Framework selection happens BEFORE knowing the outcome. Stick with the selected framework.

### Anti-Pattern 2: Process Bypass

**Description:** "This is too important for process" or "this is too small for process."

**Solution:** All decisions use frameworks. The framework varies, but the process doesn't.

### Anti-Pattern 3: Documentation Afterthought

**Description:** Making the decision, then documenting it retroactively.

**Solution:** Documentation happens DURING the framework application, not after.

### Anti-Pattern 4: Retrospection Skip

**Description:** "We're too busy to retrospect" or "the decision worked fine."

**Solution:** Mandatory retrospection for critical decisions. Optional retrospection for others.

## Success Metrics

We measure framework success along three dimensions:

### 1. Decision Quality
- Did the decision produce the expected outcome?
- Was the decision better than alternatives?
- Did we avoid predictable pitfalls?

### 2. Process Efficiency
- Did we stay within time boxes?
- Was the time investment appropriate for the decision?
- Did we avoid analysis paralysis?

### 3. Relationship Health
- Did the process strengthen cofounder trust?
- Were there residual tensions?
- Is collaboration easier or harder after the decision?

## Continuous Evolution

This meta-framework is not static. It evolves through:

1. **Quarterly Reviews:** Assess framework performance and usage patterns
2. **Retrospection Insights:** Learn from each decision's retrospection
3. **Company Scaling:** Adjust as company grows and complexity increases
4. **Cofounder Feedback:** Incorporate experience and suggestions

**Philosophy:** The framework serves the company, not the other way around. Adapt when needed, but change deliberately.
