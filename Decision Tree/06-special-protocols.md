# 6. Special Protocols

## Overview

This document covers special protocols for situations that don't fit the standard framework flow: alignment resolution, escalation, and emergency decisions.

**Key Principle:** Special protocols are exceptions, not the rule. Use them only when standard frameworks are insufficient.

## Alignment Resolution Protocol (Detailed)

### When to Use

Use Alignment Resolution Protocol when:
- Cofounders cannot agree on the problem statement
- Values-based disagreements prevent framework application
- Cofounders are "talking past each other"
- Fundamental strategic disagreements exist

### Step 1: Problem Statement Isolation

**Goal:** Separate problem definition from solution discussion.

**Process:**
- Each cofounder writes their problem statement independently
- No solution discussion allowed in this phase
- Time box: 30 minutes

**Output:**
- Cofounder A problem statement
- Cofounder B problem statement

**Common Issues:**
- Cofounders drift into solutions
  - **Solution:** Gently redirect to problem statement
- Problem statements are too vague
  - **Solution:** Ask for specific, measurable problem definition
- Problem statements include solutions
  - **Solution:** Extract the core problem, discard solution language

### Step 2: Comparison and Gap Analysis

**Goal:** Identify specific points of disagreement.

**Process:**
- Compare problem statements side-by-side
- Identify specific points of disagreement
- Categorize disagreements: factual, interpretive, values-based
- Time box: 1 hour

**Disagreement Categories:**

**Factual Disagreements:**
- Different understanding of facts
- Different data sources
- Different interpretation of data
- **Resolution:** Gather objective data

**Interpretive Disagreements:**
- Same facts, different meaning
- Different assumptions about causality
- Different predictions about outcomes
- **Resolution:** Seek external expert input

**Values-Based Disagreements:**
- Different priorities
- Different risk tolerance
- Different vision for company
- **Resolution:** Explicit values discussion

**Output:**
- List of specific disagreements
- Categorization of each disagreement
- Resolution approach for each category

### Step 3: External Data Gathering

**Goal:** Resolve disagreements with objective input.

**Process:**
- For factual disagreements: gather objective data
- For interpretive disagreements: seek customer/advisor input
- For values disagreements: explicit values discussion
- Time box: 1-2 days

**Data Sources:**
- Customer interviews/surveys
- Market research reports
- Advisor board input
- Industry benchmarks
- Competitor analysis
- Financial projections

**Values Discussion:**
- Explicitly state values
- Discuss why each value matters
- Explore if values are truly in conflict
- Consider if compromise is possible

**Output:**
- Data gathered for factual disagreements
- External input for interpretive disagreements
- Values alignment document for values disagreements

### Step 4: Re-alignment

**Goal:** Achieve agreement on problem statement.

**Process:**
- Draft unified problem statement
- Both cofounders must explicitly agree
- If still no alignment: escalate
- Time box: 2 hours

**Success Criteria:**
- Both cofounders can state the problem in their own words
- Both cofounders agree on success metrics
- Both cofounders agree on constraints

**If Alignment Fails:**
- Escalate to Advisory Board (if available)
- Escalate to Board of Directors (if constituted)
- Escalate to external mediator
- As last resort: invoke SHA dispute resolution

**Output:**
- Unified problem statement
- Explicit agreement from both cofounders
- Or escalation documentation

### Step 5: Proceed

**Goal:** Move to framework selection with aligned problem statement.

**Process:**
- Proceed to framework selection (see [04-framework-selection.md](./04-framework-selection.md))
- Document alignment resolution process
- Store in secure location

**Template:** [`./templates/alignment-resolution-log.md`](./templates/alignment-resolution-log.md)

## Escalation Protocol

### When to Escalate

**Escalation Triggers:**
- Framework application exceeds time investment by 2x
- Cofounders cannot reach agreement after framework completion
- Decision is time-critical and framework is too slow
- One cofounder believes the wrong framework was selected
- Alignment resolution fails

### Escalation Path

**Level 1: Framework Change**
- Mutual agreement to try alternative framework
- Document reason for change
- Proceed with new framework
- No external involvement required

**Level 2: Advisory Board Input**
- If Advisory Board exists, seek their input
- Present decision context and framework attempts
- Request perspective, not decision
- Document input received
- Cofounders retain decision authority

**Level 3: Board of Directors Decision**
- If Board exists, escalate decision
- Present full documentation
- Request Board decision
- Cofounders abide by Board decision
- Document Board decision and rationale

**Level 4: External Mediator**
- If no Board or Board unavailable
- Engage professional mediator
- Mediator facilitates decision process
- Cofounders commit to mediator's process
- Document mediator involvement and outcome

### Escalation Documentation

**Required Elements:**
- Trigger for escalation
- All framework attempts with outcomes
- External input received
- Final resolution
- Lessons learned

**Template:** Use framework template with escalation section added

### Escalation Best Practices

**Practice 1: Escalate Early**
- Don't wait until cofounder relationship is damaged
- Escalate when frameworks aren't working
- Better to escalate than to force a bad decision

**Practice 2: Document Everything**
- Escalation requires full documentation
- Provide context to escalation party
- Create audit trail

**Practice 3: Maintain Decision Authority**
- Advisory Board provides input, not decisions
- Board makes decisions only when escalated
- Cofounders retain authority unless explicitly escalated

**Practice 4: Learn from Escalation**
- Why did escalation occur?
- What can be improved?
- Update framework if needed

## Emergency Decision Protocol

**Problem Discovery (Gate 1):** Minimum capture, retroactive Problem Statement, and RFC/options deadlines are in [Problem Discovery/07-emergency-and-expedited.md](../Problem%20Discovery/07-emergency-and-expedited.md).

### When to Use

**Conditions:**
- Decision must be made within 4 hours
- Delay causes significant harm
- No time for full framework application

**Examples:**
- Security incident response
- Legal threat requiring immediate response
- Critical infrastructure failure
- Regulatory compliance emergency
- PR crisis requiring immediate response

### Process

**Step 1: Quick State Assessment (15 minutes)**
- What is the emergency?
- What happens if we delay?
- What are our options?
- What is the worst-case outcome?

**Step 2: Framework Selection (5 minutes)**
- Use 5-Minute Rule or RAPID
- No STOP, ASOFF, or Weighted Matrix
- Prioritize speed over rigor

**Step 3: Decision (30 minutes)**
- Make decision quickly
- Document decision immediately
- Implement immediately

**Step 4: Post-Emergency Documentation (within 24 hours)**
- Complete full documentation
- Document why emergency protocol was used
- Record decision and rationale

**Step 5: Retrospection (within 48 hours)**
- Complete full retrospection
- Assess if emergency was truly necessary
- Identify process improvements
- Consider Board ratification if needed

### Emergency Decision Template

```markdown
## Emergency Decision Record

**Decision ID:** [ID]
**Emergency Declared:** [DATE/TIME]
**Emergency Resolved:** [DATE/TIME]
**Declarer:** [NAME]

### Emergency Description
- What happened: [FREE TEXT]
- Why emergency: [FREE TEXT]
- Harm if delayed: [FREE TEXT]

### Quick State Assessment
- Options considered: [LIST]
- Selected option: [FREE TEXT]
- Rationale: [FREE TEXT]

### Decision
- Decision made: [FREE TEXT]
- Implementation: [FREE TEXT]
- Immediate outcome: [FREE TEXT]

### Post-Emergency Documentation
- Full documentation completed: [YES/NO]
- Documentation location: [PATH]
- Retrospection scheduled: [DATE]

### Sign-off
- Cofounder A: [NAME/SIGNATURE]
- Cofounder B: [NAME/SIGNATURE]
```

### Emergency Best Practices

**Practice 1: Declare Emergency Explicitly**
- Don't skip process without declaration
- Document why emergency exists
- Get agreement from both cofounders if possible

**Practice 2: Prioritize Speed**
- Use fastest appropriate framework
- Don't over-analyze
- Make decision and move

**Practice 3: Document Immediately**
- Don't wait for full documentation
- Capture decision and rationale immediately
- Complete full documentation later

**Practice 4: Retrospect Thoroughly**
- Emergency decisions deserve thorough review
- Assess if emergency was truly necessary
- Identify process improvements

**Practice 5: Consider Ratification**
- For major emergency decisions, consider Board ratification
- Ratification within 7 days
- Provides oversight without delaying emergency response

## Protocol Selection Guide

| Situation | Protocol | Time Investment |
|-----------|----------|-----------------|
| No alignment on problem | Alignment Resolution | 1-3 days |
| Framework not working | Escalation Level 1 | Immediate |
| Need external input | Escalation Level 2 | 1-2 days |
| Board decision needed | Escalation Level 3 | 1-3 days |
| Mediation needed | Escalation Level 4 | 1-2 weeks |
| Emergency (<4 hours) | Emergency Protocol | <1 hour decision, 24-48h documentation |

## Protocol Interaction with Standard Frameworks

### Alignment Resolution + Standard Frameworks

**Flow:**
1. State Assessment reveals no alignment
2. Use Alignment Resolution Protocol
3. Once aligned, proceed to standard framework selection
4. Apply selected framework
5. Complete retrospection (mandatory for Alignment Resolution)

### Escalation + Standard Frameworks

**Flow:**
1. Standard framework application fails
2. Escalate to appropriate level
3. Resolution achieved through escalation
4. Document escalation and outcome
5. Complete retrospection (mandatory for escalation)

### Emergency + Standard Frameworks

**Flow:**
1. Emergency declared
2. Use Emergency Protocol
3. Decision made and implemented
4. Complete post-emergency documentation
5. Complete retrospection (mandatory for emergency)

## Common Protocol Mistakes

### Mistake 1: Overusing Emergency Protocol

**Symptom:** Declaring emergency for non-emergency decisions.

**Solution:** Emergency is for true emergencies (<4 hour window, significant harm if delayed).

### Mistake 2: Under-Escalating

**Symptom:** Trying to force framework when it's not working.

**Solution:** Escalate early rather than damaging cofounder relationship.

### Mistake 3: Skipping Alignment Resolution

**Symptom:** Proceeding with framework when cofounders disagree on problem.

**Solution:** Always resolve alignment first. Frameworks assume aligned problem statement.

### Mistake 4: Incomplete Emergency Documentation

**Symptom:** Making emergency decision and never documenting.

**Solution:** Emergency requires immediate documentation and retrospection within 48 hours.
