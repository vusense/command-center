# 5. Framework Application Phase

## Overview

This document provides general rules and guidelines for applying the selected framework. Framework-specific templates are located in the [`./templates/`](./templates/) directory.

**Key Principle:** Frameworks are tools, not straitjackets. Apply them with judgment, not rigidity.

## General Application Rules

### Rule 1: No Framework Skipping

Every decision must use a framework from Section 4. No exceptions except Emergency Protocol.

**Why:**
- Ensures consistency
- Provides audit trail
- Prevents ad-hoc decision-making
- Maintains process integrity

### Rule 2: Documentation Mandatory

All framework applications must be documented using the appropriate template.

**Why:**
- Enables retrospection
- Supports investor due diligence
- Facilitates knowledge transfer
- Creates accountability

### Rule 3: Time Boxing

Respect framework time investments. Exceeding time boxes triggers escalation.

**Why:**
- Prevents analysis paralysis
- Forces prioritization
- Maintains momentum
- Respects cofounder time

**Escalation Triggers:**
- Framework exceeds time investment by 2x
- No progress despite time investment
- Cofounders agree framework isn't working

### Rule 4: External Input

For Type III/IV decisions, consider advisor/investor input.

**When to Seek External Input:**
- Decision exceeds cofounder expertise
- High-stakes strategic decisions
- Board approval required
- Legal or regulatory implications

**How to Incorporate External Input:**
- Document input source and content
- Treat as data point, not decision-maker
- Maintain cofounder decision authority
- Record how input influenced the decision

### Rule 5: Decision Recording

Record final decision in Decision Register after framework application.

**Why:**
- Creates master record of all decisions
- Enables pattern analysis
- Supports investor due diligence
- Facilitates retrospection

## Framework-Specific Application Guidelines

### STOP Protocol Application

**Preparation:**
- Ensure 24-48 hour STOP period is feasible
- Identify data sources for observation phase
- Schedule re-convene time

**During STOP:**
- Each cofounder writes position independently
- No discussion during STOP period
- Gather objective data
- Consider external input

**During PROCEED:**
- Share documented positions
- Review gathered data
- Discuss with open minds
- Document final decision

**Common Pitfalls:**
- Violating STOP period (discussing during STOP)
- Inadequate data gathering
- Not documenting positions
- Rushing the re-convene

**Template:** [`./templates/stop-protocol.md`](./templates/stop-protocol.md)

---

### ASOFF Application

**Preparation:**
- Ensure adequate time (1-3 days)
- Identify criteria for filtering
- Prepare options generation session

**During ASSESS:**
- Document current state thoroughly
- Identify constraints explicitly
- Define success criteria clearly

**During STAKE:**
- Each cofounder writes position independently
- Include rationale and confidence level
- Share positions before options generation

**During OPTIONS:**
- Generate minimum 3 options
- Include "do nothing" as an option
- Be creative, not just incremental

**During FILTER:**
- Use objective criteria
- Score options systematically
- Document scoring rationale

**During FINALIZE:**
- Select highest-scoring option
- Document implementation plan
- Define success metrics

**Common Pitfalls:**
- Generating too few options
- Using subjective filtering criteria
- Not documenting rationale
- Skipping implementation planning

**Template:** [`./templates/asoff-worksheet.md`](./templates/asoff-worksheet.md)

---

### ICE Application

**Preparation:**
- Ensure adequate time (1-2 hours)
- Identify options to compare
- Prepare scoring sheet

**During Scoring:**
- Score each option independently
- Use consistent scale (1-10)
- Document scoring rationale
- Calculate ICE scores

**During Selection:**
- Select highest ICE score
- Discuss if scores are close
- Document final decision

**Common Pitfalls:**
- Inconsistent scoring between options
- Not documenting rationale
- Ignoring close scores
- Using for complex decisions

**Template:** [`./templates/ice-scorecard.md`](./templates/ice-scorecard.md)

---

### RAPID Application

**Preparation:**
- Identify domain expert
- Clarify decision authority
- Ensure full alignment on problem

**During RECOMMEND:**
- Domain expert makes recommendation
- Provide rationale and data
- Document recommendation

**During AGREE:**
- Other cofounder reviews
- Agree or object with rationale
- If object, provide input only

**During PERFORM:**
- If agreed, execute immediately
- Document execution
- Monitor outcomes

**Common Pitfalls:**
- No clear domain expertise
- Using for values-based decisions
- Not documenting recommendation
- Violating agree/perform sequence

**Template:** [`./templates/rapid-log.md`](./templates/rapid-log.md)

---

### 5-Minute Rule Application

**Preparation:**
- Ensure decision is truly Type I
- Confirm low risk
- Verify reversibility

**During 5-Minute Rule:**
- Each cofounder states position (2 min)
- Quick alignment check (1 min)
- If aligned: proceed
- If not aligned: escalate to ICE

**Common Pitfalls:**
- Using for non-Type I decisions
- Not respecting time box
- Skipping alignment check
- Not documenting minimal log

**Template:** [`./templates/5-minute-log.md`](./templates/5-minute-log.md)

---

### Weighted Decision Matrix Application

**Preparation:**
- Ensure adequate time (4-8 hours)
- Identify decision criteria (5-7 max)
- Prepare options (3-5 max)

**During Criteria Definition:**
- Limit to 5-7 criteria
- Weight by importance (sum = 100%)
- Document rationale for weights

**During Options Generation:**
- Generate 3-5 options
- Ensure options are distinct
- Include "do nothing" if applicable

**During Scoring:**
- Score each option against each criterion (1-10)
- Score independently to avoid bias
- Document scoring rationale
- Calculate weighted scores

**During Selection:**
- Select highest-scoring option
- Discuss if scores are close
- Document final decision

**Common Pitfalls:**
- Too many criteria (analysis paralysis)
- Too many options (overwhelming)
- Inconsistent scoring
- Not documenting rationale

**Template:** [`./templates/weighted-decision-matrix.md`](./templates/weighted-decision-matrix.md)

---

### Alignment Resolution Protocol Application

**Preparation:**
- Ensure adequate time (1-3 days)
- Prepare for difficult conversation
- Identify external data sources if needed

**During Problem Statement Isolation:**
- Each cofounder writes problem statement independently
- No solution discussion allowed
- Time box: 30 minutes

**During Comparison and Gap Analysis:**
- Compare statements side-by-side
- Identify specific disagreements
- Categorize disagreements
- Time box: 1 hour

**During External Data Gathering:**
- Gather objective data for factual disagreements
- Seek advisor input for interpretive disagreements
- Have explicit values discussion for values disagreements
- Time box: 1-2 days

**During Re-alignment:**
- Draft unified problem statement
- Both cofounders must explicitly agree
- If still no alignment: escalate
- Time box: 2 hours

**Common Pitfalls:**
- Discussing solutions during problem isolation
- Not categorizing disagreement types
- Skipping external data gathering
- Forcing alignment when it doesn't exist

**Template:** [`./templates/alignment-resolution-log.md`](./templates/alignment-resolution-log.md)

## Sign-Off Requirements

### Required Sign-Offs

All framework applications require sign-off from both cofounders.

**Sign-Off Elements:**
- Name
- Date
- Explicit agreement or dissent
- Comments (optional)

### Dissenting Views

If one cofounder disagrees with the final decision:

1. Document dissenting view in framework template
2. Record rationale for disagreement
3. Note if disagreement is values-based or tactical
4. Document how decision was made despite disagreement

**Why Document Dissent:**
- Preserves relationship
- Creates audit trail
- Enables future review
- Supports learning

## Decision Register Entry

After framework application, update the Decision Register.

**Required Fields:**
- Decision ID
- Date
- Title
- Framework used
- Risk level
- Reversibility type
- Outcome
- Status

**Template:** [`./templates/decision-register.md`](./templates/decision-register.md)

## Common Application Mistakes

### Mistake 1: Template Incompleteness

**Symptom:** Leaving sections blank or incomplete.

**Solution:** Use templates as checklists. Complete all sections.

### Mistake 2: Skipping Documentation

**Symptom:** Making decision, then documenting retroactively.

**Solution:** Document during framework application, not after.

### Mistake 3: Violating Time Boxes

**Symptom:** Framework takes 2x longer than specified.

**Solution:** Escalate rather than exceed time box.

### Mistake 4: No Sign-Off

**Symptom:** Decision made without explicit sign-off.

**Solution:** Require sign-off before considering decision complete.

## Application Quality Checklist

Before considering a framework application complete:

- [ ] Framework template fully completed
- [ ] Both cofounders have signed off
- [ ] Decision recorded in Decision Register
- [ ] Documentation stored in secure location
- [ ] Time box respected (or escalation documented)
- [ ] External input incorporated if required
- [ ] Implementation plan documented (if applicable)
- [ ] Success metrics defined (if applicable)

## Next Steps

After framework application:

1. **Implement the decision** according to implementation plan
2. **Monitor outcomes** against success metrics
3. **Complete retrospection** if required (see [07-retrospection.md](./07-retrospection.md))
4. **Update Decision Register** with outcomes
